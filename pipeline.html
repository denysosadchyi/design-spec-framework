How this works

You are about to design a product without opening a single design tool. This page is the map. Read it once. It takes five minutes. Then use the left menu to walk the phases in order.

This folder is the design file

There is no Figma file to keep in sync, no separate document holding the "real" decisions. The research, the screens, the words on the buttons, the colours, the design system, the handoff: all of it lives here as files, and this page is the front door to them.

The screens are built once and then layered. The plain grey page you will see in phase 4 is literally the same file that gets real copy in phase 5, colour and components in phase 6, wide-screen behaviour in phase 8 and motion in phase 9. Nothing is ever redrawn from scratch, so nothing quietly falls out of sync.

Claude Code, and how you talk to it

Claude Code is an assistant that can read and write the files in this folder. You talk to it by typing in a chat window, the same way you would message a colleague. You never open a terminal, never install anything, never run anything yourself. If something needs to be created, moved, published or screenshotted, you ask and it does it.

A command here is simply a phrase you type into that chat. It starts with a slash and looks like /dsf:brief. That is not a terminal command and there is nothing to memorise: every phase page below gives you the exact text to paste. After you send it, the assistant starts asking you questions; answer them in plain language.

Two you can use at any time: /dsf:status tells you where you are, and /dsf:critique followed by whatever you want reviewed (a screen, a folder, the whole product) runs a proper review pass on it.

The prompt blocks

Every step on every phase page carries a block like this one. Press Copy, paste it into the chat, send. They are filled in with your project's own details as the project learns them. Anything still shown as ‹like this› is a blank you fill in yourself, and it will auto-fill once the phase that decides it is done.

paste into the chat
        /dsf:status

The rhythm of every phase

Every phase moves the same way. Once you have felt it once, you know how all eleven feel.

  1. One sample first. The assistant builds a single thing end to end: one screen, one component, one flow. Not forty at once.
  2. You look at it. It stops and you open the file in your browser. This is the cheapest moment to change your mind.
  3. It rolls out the rest. With the sample approved, everything else is produced against it in parallel.
  4. One defect table. Not a stream of comments per file. One table: where the problem is, what is wrong, how to fix it.
  5. You prioritise. You order the table, drop rows, or promote something into a rule. The assistant does not decide what matters.
  6. It fixes at the source. A change lands where the truth lives: the value, the component, the conventions file. From there it propagates, never patched onto one screen.

Human gates your call

At fixed points the assistant stops and waits for you. It will not guess past a gate, and it will not choose taste on your behalf. Wherever you see that chip on a phase page, nothing happens until you answer.

The decisions that are always yours: which competitors actually matter, what makes the MVP and what gets cut, which of three visual directions the product becomes, the order in which defects get fixed, and whether a phase is finished. The assistant does the work; the judgement stays with you. Every one of those answers is written to a decisions log, so nothing has to be re-litigated later from memory.

One phrase is worth knowing: when you say "keep it" about something the assistant tried, it stops being an experiment and becomes a rule, written down and rolled out everywhere it applies.

When you change your mind

You will. That is normal, and the framework is built for it rather than against it.

Before applying any request, the assistant checks it against what the project has already decided. If your request contradicts nothing written down, it just does it. If it contradicts a decision already on the record, it stops and shows you three things: the exact line it contradicts, why that line exists (the persona, the research finding, the attribute it came from), and three options:

  • Update the spec: the earlier decision changes, and the change is propagated everywhere it applies: screens, values, copy, docs.
  • A recorded exception: apply it here only, written down as a known exception so the next review does not report it as a defect.
  • Withdraw: drop it, logged, so the same idea does not get argued from zero in a month.

This is a feature, not friction. It is what keeps the folder honest: a change that lands on the screens but not on the spec breaks the whole claim that this repo is the design file.

For anything that arrives after a phase was signed off, use /dsf:change. You describe what you want in your own words and get a blast-radius table before anything is touched: which phases it invalidates, and which files move.

paste into the chat
        /dsf:change "{what you want changed, in your own words}"

Stopping and coming back

Nothing lives in the chat history, so nothing is lost when you close it. Come back in a week, open a new chat, and ask where you are: it reads the folder and tells you which phase you are in, what is finished, and the exact next thing to type. When you think a phase is done, /dsf:check verifies it against the phase's written criteria and reports pass or fail per item, with the file that proves each one.

paste into the chat
        /dsf:status

        Then, in three lines: where am I, what's finished, and exactly what do I type next?

If the assistant ever drifts, invents facts, colours a screen it was not supposed to, or fixes things you did not ask for, say so plainly. Every phase page below has an If it drifts block with ready corrections, and asking "which of these did you actually verify?" is always a fair question.

Phase 0 · /dsf:init

Init…

To get here

Why this phase exists

    Phase 1 · /dsf:brief

    Brief…

    Gives you one page every later phase reads: what you are making, for whom, on what kind of device, and how you will know in three months that it worked.

    To get here

    Finish phase 0 · Init first, then paste /dsf:brief followed by a sentence about your idea.

    Must exist first:

    • your tool record (.design/memory/toolbox.md), with no row left unanswered

    Why this phase exists

    The brief is the one artifact every later phase re-reads on every prompt. If it is vague, the vagueness is inherited by the research, the screens and the design system.

    So it is produced by questioning, not by drafting. The assistant interrogates the idea before a single file exists, and what ends up written down is your answers, not a plausible product description it composed while you watched.

    Step by step

    1. Start the phase with a seed. One sentence is genuinely enough.

      paste into the chat
                  /dsf:brief {{oneLiner}}

    2. It asks in small batches, three to five questions at a time, across five areas: who it is for, what is broken today, which device comes first, what constrains you, and how success will be observed.

      paste into the chat
                  Ask me the brief questions in batches of three to five, one area at a time. Don't draft
            anything yet, and don't answer anything on my behalf.

    3. Expect push-back. "Everyone" is not an audience; a success criterion nobody could check in three months gets sent back. Ask for it explicitly if it goes soft on you.

      paste into the chat
                  Push back where my answers are vague. If my audience is demographics, ask me for
            situation and current behaviour instead. If a success criterion can't be observed in
            three months, tell me and ask for a replacement.

    4. If you genuinely do not know something, say so. It records [?] plus its explicit guess and moves on: it will not fill your gap with a confident invention. Those marks stay visible everywhere afterwards; they are honesty, not untidiness.

      paste into the chat
                  I don't know that yet. Mark it [?], write your hypothesis explicitly, say what would
            confirm it, and move on.
    5. your call

      It plays the whole brief back in the chat and stops. Nothing is written until you approve. Correcting one area re-opens only that area, not the whole interview.

      before you approve
                  Show me the whole brief in chat before you write a single file: name, pitch, audience,
            problem, platform, constraints, success criteria, and every open [?].
      your approval
                  Approved, with one correction: {what to change}. Redo that area only, then write
            CLAUDE.md and README.md.

    6. After approval it writes the brief, the project's front page, and the empty folders later phases will fill.

      paste into the chat
                  Scaffold the folders exactly as .design/memory/phases.md defines them — no invented
            names, nothing missing — run the phase 1 checklist, then commit. Don't tag.

    What good looks like

    The brief fits on one screen. The primary device is decided and owned by you, because it constrains every phase after it. Everything unknown is marked [?] with a stated hypothesis, and the brief says what the product is not doing.

    correction

          questions, and show me the brief in chat first.
    correction
              You filled a gap with a plausible answer. Mark it [?], state the hypothesis explicitly,
          and ask me the question.

        Phase 3 · /dsf:ia

        Structure…

        Gives you the map: which screens exist, the job each one closes, and the paths a person actually walks, including the ones where they get stuck.

        To get here

        Finish phase 2 · Discover first, then paste /dsf:ia into the chat.

        Must exist first:

        • your personas and jobs (people/personas.md, people/jtbd.md)
        • your research page (research/research.html)

        Why this phase exists

        A screen with no job and a job with no screen are the same defect, and one table catches both. This phase derives the structure from what people are trying to do, not from a competitor's menu, which is the fastest way to inherit somebody else's mistakes.

        It also proves the paths: every route is walked to an ending, including the endings where a person fails and needs a way out. Dead ends and missing states are cheapest to fix here, while the product is still an outline.

        Step by step

        1. Start the phase.

          paste into the chat
                      /dsf:ia

        2. Objects before screens. It inventories the things a person actually deals with, each tied to the job that produces it. Objects nothing asks for go into a "questionable" list rather than quietly becoming screens.

          paste into the chat
                      Start with entities, not screens: what objects does someone using {{product}} deal with,
            which job in people/jtbd.md produces each one, and what relates to what? Anything with
            no job goes in a separate "questionable" list. Don't propose screens or navigation yet.

        3. The screen tree, with the job printed next to every screen. No job means [ORPHAN], not polite acceptance. Empty, error and loading are recorded as states, never as screens.

          paste into the chat
                      Derive the screen tree from the jobs, not from a competitor's menu. Print the job it
            serves next to every screen; anything you can only justify with a stretch gets marked
            [ORPHAN]. Empty, error and loading are states of a screen, not screens.

        4. Navigation: three to five top-level entries, each justified by the job behind it. Then it counts the taps to the main job: over three and it restructures or writes down the trade-off. That number becomes a budget later phases are held to.

          paste into the chat
                      Give the tree a navigation model: 3–5 global items, each with the job behind it. Then
            count the taps from the first screen to {{mainJob}} for {{primaryPersona}}. If it's more
            than three, restructure and explain the trade-off. Write the count down — it's a budget.

        5. Flows drawn as diagrams: the decision points, the "no" branches, the empty / error / loading states, and both endings: success and the places a person gets stuck.

          paste into the chat
                      Draw the flows in ia/flows.md: the main job plus 2–3 key related jobs. Every flow needs
            decision diamonds with both branches labelled, empty / error / loading as their own
            nodes, and both endings — success and the dead ends where someone gets stuck. Every
            screen node must already exist in ia/sitemap.md.

        6. A coverage table of jobs against screens. An empty row or column is a defect with a named resolution: delete it, add a screen, attach it somewhere, or backlog it on purpose.

          paste into the chat
                      Build the jobs × screens coverage matrix, then read every row and column out loud: name
            the job for each screen and the screen for each job. List the orphan screens and orphan
            jobs explicitly, and give each one a decision — delete, add, attach, or backlog.
        7. your call

          It reviews its own map for four things: dead ends, missing states, excess depth, orphans. Then it hands you the table without fixing anything. You order it.

          before it fixes anything
                      Give me the defect table only — dead ends and missing states first — and change nothing
            yet.
          your answer
                      Fix in this order: {row numbers}. Drop {row numbers} — I accept those. Fix each one in
            ia/sitemap.md first and propagate into ia/flows.md; don't patch a single diagram.

        8. Open ia/ia.html: the tree with jobs, the flows as real diagrams, the coverage table with orphans highlighted.

          paste into the chat
                      Render ia/ia.html: the sitemap tree with the job next to every screen, all flows as live
            diagrams on the dark theme, and the coverage matrix with orphans highlighted. Then
            regenerate pipeline.html.

        What good looks like

        Point at any screen and you can say which job it closes. Every flow shows at least one way to fail and the way back out of it. And you can say out loud how many taps it takes to do the main thing.
