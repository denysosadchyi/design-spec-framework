# Phases — the canonical table

This file is the **single source of truth** for the pipeline's shape: which phases exist,
which commands drive them, which checklist gates them, which git tag closes them, and which
artifacts prove they happened.

`/dsf:init`, `/dsf:status` and `/dsf:check` read this table instead of carrying their own
copies. `index.html` renders the same list. If a command and this file disagree, this file
wins — and the disagreement is a bug worth reporting.

Do not edit this file to record project progress. It describes the pipeline, not the project.
Progress lives in the files themselves (see **States** below) and, step by step, in the
append-only ledgers under `.design/progress/` (see **Step ledgers**).

## Success criteria — identity and numbering

Every phase's **success criteria** are the checkbox items of its checklist file, in file
order. Item 1 is the first `- [ ]` line in the file, item 2 the second, and so on to the
last — numbering runs straight through the section headings, it does not restart per
section. That ordinal **is** the criterion's id. There is no other identifier, no slug, no
hash.

Counting rule, so every reader agrees on N: an item is a line that begins with `- [ ]` at
column 0. Continuation lines (the wrapped rest of an item) and `<!-- check: … -->`
assertion comments belong to the item above them and are never counted as items of their
own. Headings, prose and code fences are not items.

> **Criteria ids are the checklist item ordinals.** Reordering checklist items, inserting
> one in the middle, or deleting one is a **breaking change** to the dashboard state: every
> stored ordinal after the edit point now points at a different criterion. After any such
> edit, re-run `/dsf:check <phase>` for that phase — the stored `passed`/`failed` ordinals
> are not migrated automatically and must not be hand-patched.

Appending an item at the **end** of a checklist is the one safe edit: existing ordinals keep
their meaning, `total` grows by one, and the new item is simply unverified until the next
`/dsf:check`.

## Step ledgers — `.design/progress/phase-N.md`

Criteria say whether a phase is *done*. Ledgers say **how far into it you got**, live, while it
is still running.

`.design/progress/phase-N.md` is an **append-only ledger**, one file per phase, `N` the phase
number from the table above. A two-command phase keeps one file: phase 2's ledger carries both
`research.*` and `users.*` lines, in the order the work actually happened.

### The line

Immediately after each numbered command step finishes — and immediately after each HUMAN GATE
inside a step resolves — the command that is executing appends **one line**:

```
- <command>.<step> · <step name> · YYYY-MM-DD HH:MM · files: <paths touched> [· gate: <verbatim short answer>]
```

| Field | Rule |
|---|---|
| `<command>` | the command name without the `/dsf:` prefix — `research`, `users`, `wireframes` |
| `<step>` | the ordinal of the step heading in that command file, an integer |
| `<step name>` | the step's heading text, short; no re-telling of what was produced |
| date + time | local time, 24-hour, minute precision — written when the step ends, not when it started |
| `files:` | the repo-relative paths the step actually created or changed, comma-separated. Nothing touched → `—` |
| `gate:` | present **only** on a step that held a human gate. The human's own words, verbatim, trimmed to one line |

```
- research.2 · Collect the data yourself, then build the matrix · 2026-07-31 14:05 · files: research/research.md, research/screens/
- research.3 · Benchmark — one dimension · 2026-07-31 14:31 · files: research/research.md · gate: yes, benchmark against booking flows
```

### The rules

- **Append only.** A line is never edited, reordered or deleted. Not to tidy it, not to fix a
  typo in a step name, not because the step was later redone.
- **A re-run appends again.** Running `/dsf:wireframes` a second time writes a second
  `wireframes.3` line. Both are true: the step ran twice, on two dates. The ledger is a log, not
  a checkbox list, and duplicate ids are the normal shape of real work.
- **The ledger is the resume signal.** A command **reads its own ledger before doing anything
  else** and reports, in one block, what it will skip, what it will redo and why — then starts.
  A re-run that silently repeats a finished fan-out is the failure this file exists to prevent.
- **A step with no line did not happen.** Same standard as the decision log (constitution
  rule 7): the ledger is the only evidence that a step ran, and it is written in the same pass
  as the step, before the next step begins — not batched at the end of the phase.
- **The gate segment does not replace the decision log.** The full entry — trigger, contradiction,
  option chosen, what was propagated — still goes to `.design/decisions.md`. The ledger carries
  the one-line answer so the timeline reads without a second file open.
- **Unnumbered interludes** (`## Between steps — the point edit` in `/dsf:concept`,
  `### ★ Graduation one-shot` in `/dsf:handoff`) get **no id of their own**. They belong to the
  numbered step above them and are named inside that step's line.
- **Reopening leaves a line too.** `/dsf:change` appends
  `- reopened · phase-N · YYYY-MM-DD HH:MM · reason: <one line> · see .design/decisions.md`
  to each reopened phase's ledger. It removes nothing above it.
- The ledgers are committed with the phase's work. They are project history, like the decision
  log; they are not regenerated and never rebuilt from the dashboard.

## The dashboard data block

`index.html` ships with its markup already written; its styles, dictionaries and renderer
live next to it in `assets/` (`fonts.css`, `pipeline.css`, `i18n-uk.js`, `pipeline.js`) and are
loaded with relative paths from the same repo — the page still requests nothing from outside it
and still opens straight from `file://`. The state contract is unchanged: the **only** part any
command may touch is the data block embedded in `index.html` itself:

```html
<script type="application/json" id="pipeline-data"> … </script>
```

It carries two things:

- `phases` — one entry per row of the table above: `id`, `number`, `name`, `status`,
  `commands`, `tag`, `tagged`, `artifacts[]` (`path`, `label`, `exists`, `link`),
  `criteria` and `steps` (both below).
- `context` — product facts the guide page uses to fill the per-step prompt hints:
  `product`, `oneLiner`, `benchmarkDimension`, `primaryPersona`, `mainJob`,
  `chosenDirection`. All strings, all empty (`""`) until the phase that learns them fills
  them in. An empty string means "not known yet" — never invent a value to fill a slot.
  It also carries one non-string key, `toolbox` (below).

#### `context.toolbox` — the tool record phase 0's Result page renders

```json
"toolbox": [
  { "tool": "Playwright MCP", "status": "active" },
  { "tool": "image generation", "status": "fallback" }
]
```

One entry per row of `.design/memory/toolbox.md`, in the same order as that table. `status` is
`active` or `fallback` only — `[?]` never reaches the JSON, because an unresolved row is a
`fallback` with its reason written in `toolbox.md`.

| Who | What it does with it |
|---|---|
| `/dsf:init` | writes it, at step 8, from the `toolbox.md` it has just finished: every row, no invented rows |
| `/dsf:status` | repairs it — if the key is missing, empty, or contradicts `toolbox.md`, it is rebuilt from `toolbox.md`, which is the source of truth |
| everyone else | leaves it alone |

`[]` until phase 0 runs. Empty means phase 0's Result shows the standard placeholder; non-empty
means it shows the tool table. It is never a place a tool decision is *authored*: `toolbox.md`
decides, this key reflects.

### `criteria` — the per-phase success-criteria state

Each phase entry carries exactly one `criteria` object:

```json
"criteria": {
  "total": 24,
  "passed": [1, 2, 3, 5],
  "failed": [4],
  "checkedAt": "2026-07-31"
}
```

| Key | Meaning |
|---|---|
| `total` | how many checkbox items that phase's checklist has — the N from the table above |
| `passed` | ordinals the last `/dsf:check` verified as **pass**, plus `human` items the human confirmed in that session; ascending, no duplicates |
| `failed` | ordinals the last `/dsf:check` verified as **fail**; ascending, no duplicates |
| `checkedAt` | the date of that check, `YYYY-MM-DD`. `""` means the phase has never been checked |

Rules the object must obey:

- **Only state travels in JSON.** The criteria *text* lives in the page markup and its I18N
  strings, keyed by phase and ordinal. Never copy criterion wording into the data block, and
  never let the block become the place a criterion is authored.
- An ordinal in **neither** array is *not yet resolved* — an unverified item, or a `human`
  item nobody has confirmed yet. That is a legitimate state and the page renders it as
  pending. Silence is not a pass.
- The two arrays never overlap, and no ordinal exceeds `total`.
- `total` is the checklist's real item count, not the number of items that happened to get a
  verdict.
- Fresh template state, written by `/dsf:init`: `total` per the table above, `passed: []`,
  `failed: []`, `checkedAt: ""` for all eleven phases.

### `steps` — the live position inside a phase

Each phase entry also carries exactly one `steps` object — the cached read of that phase's
ledger, so the dashboard can show *where in the phase* the work is without parsing Markdown:

```json
"steps": {
  "total": 19,
  "done": ["research.1", "research.2", "research.3"],
  "current": "research.4"
}
```

| Key | Meaning |
|---|---|
| `total` | the phase's step count — the sum of its commands' M from the table above (19 for a two-command phase like Discover) |
| `done` | step ids whose ledger line is written, in the order they were written; a re-run does **not** add a duplicate id |
| `current` | the step id being executed right now, or `""` when nothing is mid-flight |

Rules the object must obey:

- **Step ids are strings**, `"<command>.<ordinal>"`. The command prefix is what makes a
  two-command phase unambiguous: `"research.3"` and `"users.3"` are different steps of phase 2,
  and no id is ever bare (`"3"` is not a step id).
- **The ledger is the truth; this object is a cache.** `.design/progress/phase-N.md` is what
  actually happened. If the two disagree, the ledger wins and the object is rebuilt from it.
- A command sets `current` to a step id **when it starts** that step, and moves that id into
  `done` in the same pass that writes the ledger line. `current` then becomes the next step id,
  or `""` when the command ends.
- `current` is never an id that is already in `done` **unless** the step is genuinely being
  redone on a re-run — which the ledger records as a second line.
- `done` holds each id at most once, even though the ledger may hold a step twice. Counts on the
  dashboard are "how many steps are behind you", not "how many step runs happened".
- No id in `done` or `current` may name an ordinal higher than its command's M.
- Fresh template state, written by `/dsf:init`: `total` per the per-command table above,
  `done: []`, `current: ""` for all eleven phases.
- **On reopening** (`/dsf:change`): `done` **stays** — those steps did run, and pretending
  otherwise would make the dashboard lie about the past. Only `current` resets to `""`. The
  ledger keeps the full history either way, reopen line included.

Who writes what:

| Command | Does |
|---|---|
| `/dsf:init` | writes the initial block: phase 0 in progress, 1–10 locked, all artifacts `exists: false`, every `context` value `""`, every `criteria` at `total` with empty arrays and empty `checkedAt`, every `steps` at `total` with `done: []` and `current: ""` |
| `/dsf:status` | regenerates `phases` from the derivation below; **preserves** `context`, **preserves** each `criteria` object as-is (rebuilding one only when a newer results file exists), and **verifies `steps` against the ledgers**, rebuilding any object the ledger contradicts |
| `/dsf:check` | updates `phases` statuses and `tagged` on a full pass, writes that phase's `criteria` on every run — pass or fail — from the verdict it just wrote, and rewrites that phase's artifact `exists` flags to match what it just verified on disk; leaves `context` and `steps` untouched |
| `/dsf:change` | on each reopened phase: `status` back to `in-progress`, `current` back to `""`, `done` and `criteria` left intact, and the artifact `exists` flags updated to match what is actually on disk now. `context` is left alone with one exception — a context value this change made false is cleared (or replaced with the new value) and the source is named |
| phase commands | write their own ledger lines, keep their phase's `steps.done` / `steps.current` in step with them, fill their own `context` values and mark their own artifacts `exists: true`; never touch `criteria` |

Nobody rewrites the markup or the renderer. A phase shown green with a missing file is the
one lie the whole framework depends on not telling.

## States — how a phase is derived

Status is derived from files every time it is asked for. There is no state file, and nobody
ticks a checkbox anywhere.

| State | Condition |
|---|---|
| **done** | every key artifact in the table above is present and non-empty **and** the latest `.design/checklists/results/phase-N.md` says the checklist passed **and** the phase tag exists |
| **in progress** | some key artifacts present, but one of the three done conditions is unmet |
| **locked** | the phase produced nothing and its prerequisites — the artifacts of the previous phase — are missing |

Notes that keep the derivation honest:

- A file that exists but contains only `[?]` placeholders counts as **missing**.
- The **current phase** is the lowest-numbered phase that is not done.
- The **current step** inside that phase is read from `.design/progress/phase-N.md`: the last
  line is the last step that finished, and the step after it is what runs next. A phase with
  artifacts and no ledger is older than this convention — say so, do not invent its history.
- Artifacts from a later phase with an earlier phase not done is a contradiction: report it,
  do not silently accept it (constitution rule 9).
- `.design/checklists/results/phase-N.md` is written by `/dsf:check` — one file per phase,
  holding the date and a per-item verdict with evidence paths. The checklists themselves are
  read-only reference documents.
- **Reopening.** `/dsf:change` reopens a phase by setting its dashboard status back to
  `in-progress` and writing a `Reopened <date> · by /dsf:change · <reason>` line at the top of
  that phase's results file. A results file whose most recent line is a `Reopened` line has a
  **stale** verdict: the phase is *in progress* even though its tag still exists, until
  `/dsf:check` re-closes it. The tag is not deleted — history is not rewritten.
- **Reopening and `criteria`.** The reopened phase's `criteria` object is **not** cleared.
  The ticks from the last check stay visible next to the reopened banner, with their old
  `checkedAt` date — that pairing is the point: *these criteria passed on that date, and
  something since then invalidated the phase*. Only `/dsf:check` replaces them, on its next
  run. Nothing else edits `criteria` to make the page look tidier.
- **Reopening and `steps`.** Same principle: `done` is history and stays, `current` resets to
  `""`, and `/dsf:change` appends its reopen line to that phase's ledger. When the phase command
  runs again it reads the ledger, says which steps it will redo, and appends fresh lines for the
  ones it does.
